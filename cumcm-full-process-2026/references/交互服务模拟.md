# 交互式 / 外部服务类题的方法论（2026 B 题首创，可迁移到未来赛事）

## 核心工程：先建"协议忠实"的本地 Mock

外部黑盒（模拟器 / API / 交互式裁判）题的开发瓶颈通常不是算法，而是**资源**：
账号限次、单设备独占、正式测试次数稀缺、真实服务随机生成案例。

> 应对：按官方协议**逐条还原**一个本地 Mock（计时规则、边界语义、返回码），
> **并写一份自检脚本验证它**（协议分支、计时增量、幂等、几何/业务判定）。
> 自检全绿之前，不要让任何人基于它开发——错误的裁判比没有裁判更糟。

2026 B 题实测：本地 mock 工具（mock_sim.py / runner.py / sample_robot.py / selftest_mock.py），
29 项自检全通过后才交付给两名队员并行开发。详见 `cumcm-2026-project` 的
`references/mock-and-parallel-versions.md`。

## 五条可迁移结论

1. **公平对拍只能在固定 seed 的 Mock 上做**：真实服务随机生成案例 → 两版各跑一次的结果不可比。
2. **限次资源当战略资源**：正式测试次数只给最终择优整合版，设演练准入门槛（真机 ≥N 局 + Mock ≥M 局）。
3. **先确认资源约束再排分工**：单设备登录 / 独占账号这类约束会直接否决"多人并行"方案。
4. **反作弊纪律**：Mock 的真值调试端点（如 `/_truth`）严禁写进正式代码——真实服务没有它。
5. **不要替队伍写策略**：当采用"双版本独立开发 + 对拍择优"时，代写等于把两版合并成一版，毁掉设计。参谋只做工具/统计/审查/文档。

## Mock 自身的常见坑

- 自检首轮失败**先怀疑测试脚本**：把绝对量当增量比、在目标已被修改后才验证目标行为——都是断言写错，不是被测对象错。
- 虚拟时间只记账不 sleep → 单个 Mock 可跑 1000 局只需几秒；现实时间预算默认不强制。
- 端口要与真实服务错开（真机 2026 → Mock 用 12026），两者才能同时运行。
